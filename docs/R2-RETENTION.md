## 保留规则

Rivloom 使用完整安装包更新，不依赖逐个中间版本的补丁。每个对外发行的版本上传独立文件，当前下载与更新入口指向选定版本；无需永久保留全部历史安装包。

| 对象或条件 | 处理 |
| --- | --- |
| 当前官网下载页、`releases/latest.json`、`updates/stable/latest.json` 引用的安装包及配套校验文件 | 始终保留；几个入口暂时指向不同版本时，全部保护 |
| 最近 3 个正式版本 | 保留这些版本的发行文件；按规范版本号排序，不按文件名字典序或上传完成先后排序 |
| 距正式发布时间不超过 30 天的包 | 保留；按 UTC 滚动 30 × 24 小时计算，恰好 30 天仍保留 |
| 各版本签名清单、版本记录和清理审计记录 | 长期保留；小型历史记录不代表旧安装包永远提供下载 |
| 来源、版本、时间或引用关系无法可靠确认的对象 | 保留并记录待核对原因，不猜测后删除 |

**上表采用并集：满足任意保留条件就不能删除。** 只有确认属于已发布正式版本、已超过 30 天、不在最近 3 个版本内且不被当前入口引用的旧安装包，才进入清理候选。与该包配套的 `SHA256SUMS.txt` 可一同删除；两个 `latest.json` 和 `updates/stable/<version>.json` 不属于删除对象。

同一版本有多个构建时，保留窗口内保留全部对应构建。发布时间以可追溯的正式 Release 记录为准，不用 R2 上传时间冒充发布时间；对象最近 30 天被重新上传或修改时也暂缓删除。记录缺失、日期异常、对象无法绑定到发行记录或发现未知路径时保留。

历史签名清单仅用于追溯，不将每份历史清单里的旧 URL 当作永久保留条件，否则无法淘汰任何旧包。删除旧包后，旧直链可能失效；保留窗口不承诺旧链接永久可用。当前版本仍必须能从官网和更新入口完整下载。

## 每次正式发布的执行顺序

1. 完成本次提交的 CI、隔离安装、Release、R2 公开下载及签名更新发布；确认官网实际部署和中英文下载页已更新。仅收到 Pages Hook 成功不算部署完成。
2. 读取并验证当前两个 `latest.json` 和正式下载页的实际文件引用，列出正式发行版本、发布时间与 R2 对象。候选、新上传对象和任何仍在进行的发布均不能被误当作过期包。
3. 先生成清单，逐项标记“保留 / 可删除 / 暂缓”及理由。按上述并集规则选择候选，限定为该下载桶内明确识别的正式安装包及其配套校验文件；不递归清空桶，不匹配未知前缀。
4. 清理与发布使用同一互斥范围；CI 中沿用 `public-rivloom-download` 并发组，手动操作也须避免与发布同时进行。真正删除前重新读取入口与对象状态；状态变化则重新计算，无法确认则暂缓，不能用过期清单继续删除。
5. 只删除已核对的精确对象键。部分失败时记录已删除和未删除项，后续从实际存储状态重新核对；不通过回退当前下载或更新指针处理清理失败。
6. 删除后核对 R2 对象状态，并重新验证当前公开下载、签名清单和官网链接可用；保存结果。CDN 中仍可能暂存旧对象，不能把缓存命中当作 R2 删除失败，也不能把 R2 删除当作所有边缘缓存已立即失效。

每次收尾记录检查时间、触发版本与源码提交、当前受保护入口、逐项保留/删除/暂缓理由、删除结果和公开入口复核结果。没有候选时写明“检查完成，删除 0 个”；检查或删除未执行、失败、暂缓时如实记录，不能省略该项后声称完整维护完成。内部清单和报告不得包含凭据，也不放入公开网站静态资源。

## 自动化状态与后续约束

当前 `scripts/ci-website-download.ts` 上传发行文件并推进官网下载记录，`scripts/ci-updater.ts` 发布签名清单。它们没有列举和删除旧 R2 包的逻辑，**本规则目前通过发布工作约定与收尾检查执行，并非无人值守自动清理**。

以后接入自动化时，必须实现同一套保留判断、先生成清单、发布互斥、删除前复核和删除后验证，记录失败与实际删除结果。测试至少覆盖：版本数不足 3、30 天边界、最近 3 个版本已很久未更新、当前入口保护排名之外的版本、两个入口不一致、未知对象/时间异常、重复执行、并发发布和部分删除失败。

不得直接给整个 `releases/` 或整个桶设置“超过 30 天删除”：长期不发新版时，这会把仍然在用的最新安装包也删掉。Cloudflare 生命周期支持按时间和路径前缀处理对象，但不替 Rivloom 判断当前下载与签名引用。[Cloudflare 对象生命周期](https://developers.cloudflare.com/r2/buckets/object-lifecycles/)

GitHub Release、源码、签名密钥、用户项目、本机应用数据及升级备份不属于本策略的删除范围。若以后新增频道、平台或必须经过某版迁移的升级路径，先补充其保护规则和验证，再让该范围参与清理。
