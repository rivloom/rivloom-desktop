# M3.4 安装包与覆盖升级验证

授权：用户要求继续准备新版安装包，用于两台 Windows 的 M3.4 核心验收。

## 实施顺序

1. 将本次内测版本标为 0.1.1，保留应用 identifier、默认数据目录和官方 OpenCode 1.18.25。不升级依赖，不改防火墙、签名或自动更新。
2. 重建前保留旧 0.1.0 安装器作为升级测试基线；重建前端、运行资源、Release 和 0.1.1 NSIS。
3. 在仓库 `.data` 的新隔离目录运行真实安装器：旧版安装/启动 → 创建普通项目及未执行任务 → 关闭 → 新版覆盖升级 → 核对 Node/Brain ID、项目、任务和执行策略 → 重启 → 卸载并确认测试数据保留。
4. 验证安装产物确实含 M3.4 自动 Brain/共享 Worker 界面与后端。测试只用本机模型夹具，不读取用户 Key 或调用真实模型。
5. 更新 HANDOFF、MILESTONES、PROGRESS、VERIFICATION 及物理验收清单，交付新安装器与两台机器的升级步骤；物理 M3.4 MVP 仍由用户确认。

## 安全边界

- `/D` 仅指定安装目录，不隔离 NSIS 注册表。测试包装器只记录并恢复两个确切的 Rivloom 安装元数据键；不修改其他注册表、原应用目录或用户工作区。
- 安装使用 `/S /NS /UPDATE /D=<已验证测试目录>`，避免快捷方式和自动卸载旧应用。卸载仅调用本轮测试目录中的 `uninstall.exe /S /UPDATE`，不清除用户数据、跳转列表或自启动设置。
- 安装/升级/卸载前确认没有 Rivloom 窗口运行，防止 NSIS 的按名称终止逻辑影响用户任务；测试进程只按自己创建的 PID 清理。
- Node/PowerShell 包装器都校验测试根目录在仓库 `.data/installer-smoke/` 下；失败时保留隔离数据用于诊断，不递归删除用户目录。
- 测试不建立 Project 文件快照或内容哈希；只核对已知测试记录和单个测试标记。官方运行时供应链完整性检查保留。
- 本机覆盖升级检查不是干净 Windows 虚拟机矩阵，也不是代码签名或商业发行验收。
