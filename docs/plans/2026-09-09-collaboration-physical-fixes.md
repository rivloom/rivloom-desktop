## 已复现的问题

1. 真实规划模型把 FFmpeg/Python 软件能力放进文件 `resources`，严格校验拒绝，尚无业务执行。文件引用 schema 没有说明 64 位标识要求、软件与文件的区别。
2. `.txt` 查询被模型填为 `kinds: ["file"]`，未命中文档；下一次回复同时包含 query 和 plan 两个 JSON，校验拒绝。当前没有有界格式纠正。
3. 模型用 `gpu: false` 表达不需要 GPU，匹配器却排除了所有有显示适配器的机器，普通文件步骤永久等待。删除这个尚未开始步骤的多余条件后，原任务立即开始取材。
4. 底层规划会话显式继续可恢复为有效结果，但根 Workflow 已终止，界面没有重新规划入口。失败规划队列仍显示已保留记录；实际槽位计算已排除 failed，不能把该显示问题称为阻塞所有后续执行。
5. 本机目录节点的 `name` 使用工作文件夹名，给模型的本机名称与配对方名称不一致。
6. `@` 转交实测中，规划把用户明确的“不运行命令”约束省略了。源端写完检查点后调用 `Get-ChildItem`，保守的进程静止校验拒绝转交；源端记录完成不等于根协作完成。已把用户完整需求传给每个业务步骤和后续转交，不降低任意命令的静止校验要求。

首次失败保留，不计为通过。补充文件/软件说明后，第二次自动计划形成了四步 DAG。锁定取材补测使用实际目录引用，并通过正式的未开始步骤编辑 API 去掉了 GPU 条件；不能把这两项补测表述为原始需求一次成功。

## 修正范围与验证

- 对齐规划 schema 与真实文件引用校验；说明查询分类、软件能力、硬件要求及上游附件路径。
- `gpu: false` 表示没有 GPU 要求，CPU 工作仍可在有 GPU 的机器执行。
- 只为只读规划提供最多两次格式纠正，持久化次数和原执行记录；不重做业务步骤、不在重启后重发不确定请求。
- 规划格式失败可释放已结束的规划队列记录；业务失败或不确定状态继续保留原停止确认规则。
- 终止于规划阶段的任务提供显式重新规划入口，保留原任务与历史尝试。
- 资源目录显示真实 Node 名称。
- 执行上下文完整保留用户需求；优先截断目录证据和进度，不截断用户约束。超出协议容量则在派发前明确失败。

验证须覆盖首次失败输出、重试上限、暂停/停止/重启边界和没有重复业务执行；补测真实文件与双机依赖流程。修正源码的隔离检查与新包解包校验不能替代新包安装后的双机验收。
