# 并行选机与回复页面一起交付

用户要求同时修复独立分支未并行的问题和回复页面层级。此前的回复层级代码继续保留：最终结果和交付文件在上方，计划、横向流程图、步骤回复和执行记录位于默认折叠的“执行过程”，历史选择不会替换主结果。执行中的步骤入口现在带有实际阶段标签，区分执行中、已入队和等待处理。

## 选机修复

原选机先选目标，再等待输入取回、转存或远端上下文确认。多个分支可能在队列尚未更新时同时选择同一 Node，造成另一台合适设备空闲。

现在准备阶段同步登记临时选机占用；持久执行意图写入后由执行记录接替。负载评分取队列报告与本协调器已知未结束执行数的较大值，再加尚未提交的准备工作，避免把同一执行与其队列报告重复计算。该记账跨同一协调器的多个工作流共享，重启时从持久记录恢复；停止、失败、步骤编辑或准备放弃会释放临时占用，未确认结束的执行仍计入负载。取材后重新检查候选能力和负载，输入转存后再次核对目标仍满足条件。

空闲且满足资源、软件、硬件与授权条件的机器优先；步骤 nodeID 和单 @ 首选在负载相同时优先。@@ 锁定仍限制所有执行所在机器，已开始的执行、同机查询续接和明确目标的转交不会因为负载重新派发。单台 Node 仍一次执行一个步骤；本轮修复利用多台合适 Node 的并行能力，不改变单机执行槽和项目占用约束。

并发准备触发队列提醒时，只暂停需要该确认的步骤；较早且仍满足实际队列准入检查的步骤可以继续。实际接收端的队列提醒和准入检查保持生效。

## 验证

62 项定向测试通过，覆盖异步输入取回、转存和提交、延迟队列报告、多工作流同时派发、首选/锁定/续接、重启、停止、能力变化和排队确认，并包含回复结果选择及既有队列/文件检查。

16 项隔离双服务检查通过。新增场景没有预设分支 nodeID，保留一个首选 Node，并让两个分支取回实际注册的输入文件；两台服务上的官方 OpenCode 会话同时进入运行状态，两份模型请求均被测试闸门持有后才一起释放，记录到重叠区间，且汇合步骤此前没有执行。另验证实际文件传递、普通工具审批、转交、停止和重启。模型回复来自本地受控端点，无付费模型请求。证据：`.data/workflow-service/1788950560202/`，关键结果复制到 `.data/verification/parallel-fix-20260909/`。

14 项生产 UI 检查通过，包含结果固定、过程折叠、历史选择、多终点、单步骤、中英文、窄窗口、审批/问题/队列操作、文件定位/另存/重试，以及执行与排队状态区分。已检查相应截图。

最初受限环境不能调用 Windows DPAPI，测试节点未能启动；隔离双服务在获准的正常 Windows 环境重新运行并通过。另修正测试启动时过早读取节点身份及旧固定分工断言，不把这些失败计为通过。候选目录 `.data/verification/parallel-reply-candidate-20260909/`；由用户自行安装。未修改已安装客户端或历史任务，本轮不宣称此前真实模型业务验收问题已全部解决。
