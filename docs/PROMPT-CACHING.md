# 厂商缓存与 Agent 的关系

研究日期：2026-09-14。结论是**厂商实现缓存，Agent 的请求方式决定可复用的机会**。桌面工具说“缓存高”，通常说的是发出的模型请求有较多输入 Token 被厂商缓存命中。不能仅据此判断它自己实现了推理缓存，也不能直接判断它的总花费最低。

## 谁负责什么

厂商保存模型计算所得的前缀状态，决定模型适配、缓存边界、有效期、路由及计费。客户端仍要按厂商协议组织输入。DeepSeek 的缓存默认开启，但必须匹配已经建立的完整缓存前缀单元，公共前缀可能需要先被检测并落盘；不是两次输入开头相同就保证立即命中。[DeepSeek 官方说明](https://api-docs.deepseek.com/zh-cn/guides/kv_cache/)

Agent 控制系统提示词、工具定义、项目说明、历史消息及新信息的排列。如果每轮都改写开头、重排工具，或把不断变化的时间戳放在前面，就会减少可复用部分。Claude Code 的官方文档明确解释了它如何保持前面的系统与项目上下文稳定，把新消息追加到后面；部分模式切换也通过追加消息保持原前缀。[Claude Code 的缓存设计](https://code.claude.com/docs/en/prompt-caching)

可以用一个示意理解（是否真正命中还取决于厂商规则）：

```text
第 1 次：固定说明 + 固定工具 + 已有历史 + 新消息 A
第 2 次：固定说明 + 固定工具 + 已有历史 + 新消息 A + 回答 + 新消息 B
         └──────── 有机会复用的既有前缀 ────────┘
```

## 不同厂商还需要不同处理

| 范围 | Agent 应关注的事 |
| --- | --- |
| OpenAI | 保持前缀和历史稳定，按所选模型使用适用的显式/隐式缓存边界、缓存键及保留设置。不同代际模型的缓存边界和费用规则存在差异，不能套用旧教程 |
| Claude API | 按接口支持选择自动 `cache_control` 或显式断点；把稳定内容放在合适的断点之前，注意工具、system、消息之间的层次 |
| 模型切换、上下文压缩 | 可能改变缓存匹配条件；要结合模型和最终请求评估，而不是只看桌面会话 ID 是否相同 |

依据：[OpenAI Prompt Caching](https://developers.openai.com/api/docs/guides/prompt-caching)、[Claude API Prompt Caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)。缓存键不会让本来不匹配的内容变成缓存命中；供应商路由、账户隔离和负载等条件也不全由 Agent 控制。

## 如何判断“缓存高”是否有价值

比较相同任务、模型、服务商和账号条件，至少同时看：未缓存输入、缓存写入、缓存读取、输出 Token、整项任务实际费用、首次输出等待时间、最终任务质量。不同 API 的字段口径要先统一，不能把已经包含缓存的输入总量再次相加。DeepSeek Chat 的 `prompt_cache_hit_tokens` / `prompt_cache_miss_tokens` 可直接帮助核对命中情况；其他接口应按其 `usage` 定义读取。[DeepSeek usage 字段](https://api-docs.deepseek.com/zh-cn/guides/kv_cache/)

下面是自行构造的算术例子，不是任何厂商报价：假设缓存读单价为普通输入的 10%，暂不考虑写入和输出费用。A 工具每次输入 100,000 Token，90% 命中，等价输入成本为 `90,000 × 0.1 + 10,000 = 19,000`；B 工具输入 20,000 Token，60% 命中，等价成本为 `12,000 × 0.1 + 8,000 = 9,200`。A 命中率更高，B 却更省。提高命中率不应靠塞入无用内容或制造额外请求。

缓存复用输入的计算状态，模型仍会生成新回答，并不等于把上次回答原样返回。文件读取结果缓存、HTTP 缓存、构建缓存和模型前缀缓存也是不同的统计对象。[OpenAI 缓存常见问题](https://developers.openai.com/api/docs/guides/prompt-caching)

## 对 Rivloom 的判断

源码核对发现：`server/workflow-prompts.ts` 已把稳定协作规则放在 `workflowSystemPrompt` 中，变化的资源与业务内容放在用户消息；`server/task-service.ts` 将请求交给官方 OpenCode 的会话接口。原有架构在新轮次、规划或业务步骤之间可能创建新的引擎会话。以上是代码事实。

由此推断：同一步内的多次工具调用可能复用越来越长的上下文；跨规划、步骤和轮次则需要考虑系统规则、权限、模型、材料及引擎缓存键是否仍能复用。**新会话不必然意味着全部缓存失效，旧会话也不保证高命中。**这些是结合厂商规则的工程推断，不是实测结果。

目前 Rivloom 没有经验证的缓存命中率/费用统计，现有模型接入功能也没有额外的“提高缓存”开关。本轮没有改写工作流提示词或声称优化已上线。若后续开发缓存优化，应先采集官方引擎返回的用量元数据并区分缺失值，完成同任务对照，再决定是否调整上下文；不能为追求命中率削弱权限、混用账号或省略必要的业务信息。
