## 背景与代码事实

- `@Node` 使用直接 remote-task 邀请；自动分配使用 BrainTask + Execution。这两条已有路径不同，本轮保留各自归属，不迁移旧 Task。
- 直接邀请先自动 accepted，再检查执行能力、模型和空闲槽。普通忙碌时已接收记录等待，符合指定目标的方向；目前缺少等待原因和权威排位。
- 右侧队列按创建时间显示，而后台远程任务处理遍历的记录按更新时间排序，界面顺序不保证执行顺序。
- `WorkerRegistration` 已有硬件、负载和槽位，其严格字段校验不允许随意新增队列字段。Brain 的 `queueDepth` 也不是 Node 的等待数量。
- 当前草稿正文与 `targetNodeID` 分开保存，切换会话会清空后者；HTTP 新建每次产生新的邀请 ID，现有信道幂等不能避免用户在创建响应丢失后重复创建。
- 自动分配提交方只为本机 hosted Brain 排除 Master 自身，远端 Master 调度又总是排除自身，存在候选与实际执行能力不一致。

## 已接受决策

### 1. 指定目标与自动选择分开表达

草稿保存结构化执行目标：本机、指定 Node 或自动选择。指定 Node 绑定稳定 Node ID；原名、图标和本地备注只用于显示。切换会话、修改备注或节点改名不能改变执行目标。目标暂时不在目录、信任被撤销或出现同名节点时，不回退到本机或其他 Node。

普通繁忙、零空闲槽和短时 CPU 高允许向指定 Node 入队。例外由目标 Node 的真实接收状态和持续异常证据判断；发起端资源快照只是提示。异常也不授权系统自行改派。

本轮保留离线时明确失败并保留草稿的行为；首次发送即离线的持久信箱属于 P1。已经创建的投递继续沿用持久记录、原 ID 和有界重试/过期规则。

### 2. 收件、排队、执行是三个不同事实

本机 API 返回成功只说明本机保存了投递；对端持久保存且经认证确认才可显示送达；加入对端队列才可显示已入队；实际 OpenCode 运行才显示执行中。

可信任务默认自动收件入队，保留 ADR-0003，不恢复逐任务邀请审批。关闭执行能力表示暂停执行，已收任务可继续等待；若未来需要彻底停止收件，应使用独立、明确的接收策略，不能复用 execution enabled 字段偷换语义。

等待原因包括排队、等待槽位、节点暂停执行、模型不可用、等待项目、待审批/输入/验收和状态待确认。旧节点未提供某个事实时显示未知，不把缺失值当作 0。

### 3. 一个 Node 维护自己的持久等待队列

使用已有 SQLite 增加 Node 队列元数据，引用本机 Task 或 incoming remote-task ID，不复制业务任务、不替代 BrainTask 权威状态。保存唯一引用、接收顺序、手工顺序、暂停标记、版本号和终止原因；入队幂等。

本机与远端新任务按 Node 的接收顺序进入队列，默认不按来源插队。Node 所有者可调整尚未执行项的顺序、暂停/恢复自动启动、拒绝尚未执行的工作。发起方只控制自己的任务，不得查看或重排其他来源的任务详情。

新增队列与远端 JSON 记录之间需要可恢复的写入顺序：先持久保存 offer，再幂等建立队列，持久成功后才确认入队。启动时按稳定引用对账；已拒绝/取消的标记必须保留，不能因扫描到 accepted 邀请而复活。结果不确定时保守等待，禁止再建第二个 session。

队列等待项不预建一批 remote `ready` 业务任务占住槽。只在最终准入成功后创建/绑定实际业务 Task，所有入口共用 `WorkerAdmissionGate` 和项目锁。

M3.4 未接受的新分配也必须经过该 gate；已有可执行队列优先时可以在接受前拒绝该次分配，由原 Brain 按已有规则处理。已经接受或预留的 M3.4 Execution 要兑现原承诺，不能通过队列排序使它丢失归属、被隐式重派。review、interrupted 和执行结果未知继续按现有规则占槽。

新本机会话在用户发出执行请求后可排队自动启动；旧版本遗留的本机 open/ready 不在升级时自动执行，需要原有授权或用户主动加入自动队列。

### 4. 队列控制语义

- 调整顺序：只改尚未准入的项，使用版本检查防止旧界面覆盖新顺序。
- 暂停：暂停该排队项或后续自动启动，不挂起正在运行的 OS 进程。
- 正在执行：沿用现有“停止执行”，确认停止后才能释放槽；恢复沿用同会话补充要求，不回滚文件。
- 拒绝：表示 Node 不再执行该项，保存原因并通知发起方。已 accepted 的邀请不能调用只接受 pending 的 `decide('declined')`；需要新的队列终止回执，保持历史 accepted 事实。
- 已开始或状态未知的执行：先完成现有停止/确认流程，不能直接删除队列项并宣称任务未执行。

### 5. 目录只共享统计，任务回执只给对应来源

通过协商的新 capability 共享 Node 等待数量、是否暂停、队列更新时间、保守的健康提示；CPU/GPU 和槽位复用已有报告。保持 v1 WorkerRegistration 字段集，不把队列统计直接塞进其 strict 校验对象。

单任务队列回执携带原路由、独立递增队列版本、当前排位和原因；队列变化不得伪造递增的 Execution 进度。重连后交换最新快照，旧回执不能覆盖终态。对于 BrainTask，沿原 Worker → owning Master → submitter 路由更新最小状态。

队列排位是带时间的当前执行候选位置，会因暂停、调序和准入条件变化而变化；不承诺精确开始时间。向其他节点只共享统计和它自己任务的回执，不共享他人的任务名称、正文、本地路径、模型、额度、凭据或本地备注。

新旧节点继续支持原始任务执行。旧节点不支持队列回执时显示“对端未提供队列信息”；不能让新字段破坏旧解码，也不能把旧方无法确认的终止操作显示成两端已同步成功。

### 6. 严重异常采用保守、可解释的规则

普通排队和瞬时负载不是异常。CPU/GPU 利用率也不能单独证明模型响应性能差。

队列拥堵依据实际待执行数量和等待年龄；疑似停滞还要排除正常运行、人工暂停、待审批/输入/验收、模型或项目不可用等明确原因；通信心跳只证明在线，不代表工作取得进展。资源异常必须有新鲜、连续的采样证据，缺失/过期只显示未知。

MVP 用可配置阈值和可注入时钟实现规则，先保守告警。只有接收容量达到本机明确上限或本机明确返回不可接收时拒绝新投递；持续性能较差提示继续等候或由用户更换 Node。具体发布阈值在隔离负载验证后确定，计划不凭当前单槽文字夹具承诺通用阈值。

本轮实现采用以下**可配置内测初值**：等待项接收上限 1000；拥堵提示为至少 100 个等待项且最老等待至少 1 小时；在有空闲槽且排除了暂停/前置条件的情况下，5 分钟无取队列进展提示疑似停滞；CPU/GPU 至少一个指标连续达到 95% 满 2 分钟提示资源异常；资源采样新鲜度和最大连续采样间隔均为 20 秒。单点尖峰、旧报告、正常长任务和人工等待不据此改派。边界单测覆盖规则，少量确定性服务夹具不代表生产负载调优或通用性能阈值已经验证；界面不预测排队分钟数。

### 7. 自动分配修复采用可控范围

抽取“该 Brain 实际可调度的 Worker”规则，在提交候选和 Master 调度共用。P0 沿用当前实现不自动调度 Master 自己的限制，对每个 Brain 均按该 Brain 的 masterNodeID 过滤；Node 仍可作为其他 Brain 的 Worker。

这修复候选与执行规则不一致，不等于实现 Master 自身完整执行路径。后者需要本地 dispatch、准入、持久绑定和回执的独立设计，暂不混入此修复。

修复验证前可暂时隐藏自动分配创建入口，专用验证通过后恢复，已有会话保留。无候选应在新建前解释原因；已持有的 queued Task 保持原 Brain，合格 Worker 出现后继续原 Task，不通过另建任务掩盖失败。

## 备选方案及取舍

| 方案                               | 结论                                                                  |
| ---------------------------------- | --------------------------------------------------------------------- |
| 只为现有前端队列加按钮             | 不采用，无法保证执行顺序、恢复和远端一致性                            |
| 将直接 @ 全部迁入新 Brain 调度协议 | P0 不采用，扩大迁移、归属和重试语义，现有直接通道足以支持固定目标     |
| 删除 scheduler 的 self 排除        | 不采用，当前发往 Worker 依赖远端节点/通道，删条件不能构成本地执行闭环 |
| 暂停意味着挂起 OpenCode 进程       | 不采用，沿用可确认的停止/继续语义                                     |
| 新增消息中间件或云队列             | 不采用，现有 SQLite、持久协议记录和加密连接可覆盖 MVP                 |

## 后果与验收

主要成本集中在等待队列的持久化、竞争准入、恢复和兼容协议，工作量明显高于单纯 UI 改动。受益是目标选择、实际执行顺序和用户看到的状态一致。
