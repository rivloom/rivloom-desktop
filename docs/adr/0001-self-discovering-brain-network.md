# ADR-0001：自发现节点与多 Brain 协作网络

## 状态

提议。产品方向已由用户确认；协议细节需通过 Windows 原型和两台真实设备验证后转为“接受”。

## 背景

Rivloom 不是一台执行主机加若干远程访客，也不以“创建协作空间”作为协作起点。安装 Rivloom 的设备应成为长期在线或按需在线的节点；同一网络中的节点自动发现彼此，共同提供人、AI、模型额度、代码工作区和计算能力。

这个模型需要同时适用于个人与企业：个人可能只有一位用户和两台电脑，企业可能有多位成员、多个工作区和多个任务协调单元。当前仍由一人开发，必须先做能验证产品方向的最小协议，不能直接建设复杂共识系统、云控制平面或完整组织权限平台。

OpenCode 仍是唯一执行引擎。它只在实际执行任务的节点本机监听 loopback，不成为节点间协议，也不直接暴露给局域网或公网。

## 术语

- **Node（节点）**：一个 Rivloom 安装实例，拥有稳定设备身份、网络端点和能力描述。每个节点都能显示界面；具备项目环境的节点还能执行任务。
- **Brain**：由某个节点承载的逻辑任务协调单元，负责成员、任务状态、审批、事件和产物索引。网络中可以有一个或多个 Brain。
- **Owner Brain（归属 Brain）**：创建并持有某项任务权威状态的 Brain。一个任务在同一时刻只有一个归属 Brain。
- **Executor Node（执行节点）**：获得任务执行租约、在本地工作区调用 OpenCode 的节点。
- **Trust Domain（信任域）**：已互相确认身份、允许交换 Rivloom 业务消息的一组节点。被发现不等于已受信任。

## 决策

### 1. Rivloom 启动后自动成为可发现节点

桌面应用运行时默认发布最小的 mDNS/DNS-SD 服务，并监听同网段其他 Rivloom 节点。针对 Windows 多网卡环境下 mDNS 可能单向失效的情况，同时使用 Rivloom LAN UDP 回退：节点从临时随机端口向各本地私有子网发送查询，固定 UDP 43531 端口只接收查询并向来源临时端口单播回复。两条发现路径都只产生候选地址，节点仍须通过随机挑战和 Ed25519 签名校验后才会显示。发现数据只包含协议版本、随机节点 ID、产品端口、公开密钥指纹和 Brain ID，不包含用户名、项目名称、本地路径、任务内容、模型凭据或组织信息。

界面直接显示“附近节点”和可用 Brain，不要求用户先创建协作空间。若 mDNS 与局域网 UDP 都被 VLAN、访客网络或系统策略阻断，后续允许输入一个已知节点地址作为发现种子；这是发现回退，不改变节点协议。

### 2. 自动发现与授权分开

附近节点会自动出现，但首次建立信任仍需双方确认短码或密钥指纹。只有受信节点才能读取 Brain 信息、加入任务或请求执行。节点身份使用安装时生成的密钥对；Windows 私钥通过系统保护能力保存，业务数据库不保存可导出的明文私钥。

个人模式使用双端确认完成配对。企业模式后续可使用管理员签发的设备证书或策略自动批准，但复用同一节点和 Brain 协议。

### 3. Brain 是可并存的逻辑协调单元，不选举全网唯一主机

每个 Rivloom 节点都具备承载 Brain 的能力。首次运行可自动提供一个默认 Brain；附近节点加入后可以共用它，也可以保留自己的 Brain。网络中不存在必须选出的全局唯一 leader。

一个 Brain 负责其任务的业务状态和审计。多个 Brain 通过签名的任务委派、审批和结果消息协作，不共享一个可同时写入的 SQLite 文件。

### 4. 每个任务只有一个权威归属 Brain

归属 Brain 为任务生成全局 ID，保存任务状态机、参与者、审批要求、事件序列和产物摘要。其他 Brain 或执行节点只能依据协议提交事件和结果，不能直接修改归属 Brain 的数据库。

跨 Brain 委派使用幂等消息、单调事件序号和有期限的执行租约。MVP 不做自动转移任务所有权；归属 Brain 离线时，该任务暂停写入并清楚显示离线状态，不能由另一 Brain 静默接管。

这个单任务单写者规则支持多个 Brain 协作，同时避免在 MVP 中引入 Raft、分布式事务或多主数据库冲突解决。

### 5. OpenCode 始终留在执行节点内部

归属 Brain 只发送 Rivloom 任务、审批和控制消息。执行节点在经过授权的本地项目中启动官方 OpenCode，并把结构化进度、审批请求、差异和产物摘要回传。节点间永远不代理 OpenCode 通用 API、密码或模型凭据。

项目目录不会因为发现节点而自动共享。执行节点必须先由本机用户授权一个工作区；Brain 看到的是工作区能力和项目标识，不是可任意访问的本机文件系统。

### 6. 同一协议覆盖个人与企业

个人场景默认目标是 1 至 5 个节点、一个或少量 Brain。企业早期目标是单个信任域内 2 至 20 个节点、多个 Brain。跨子网发现、企业目录、策略下发、长期离线同步和云中继是后续能力，不在当前 M3 直接实现。

网络传输层不是产品版本名称。首个验证环境使用同一局域网，是为了先验证自发现与真实节点协作；后续可以增加企业 DNS-SD、已知种子和受保护中继，Brain 与任务语义保持不变。

## M3 实施切片

### M3.1：节点身份与自发现

- 创建稳定节点 ID 和设备密钥；重启后身份不变，卸载后的处理有明确说明。
- 在 Windows 上发布和发现 Rivloom mDNS/DNS-SD 服务，并提供 UDP 查询/单播回复回退。
- 桌面端增加节点面板，实时显示附近节点、协议兼容性、在线状态和公开指纹。
- 先用同机多个独立实例做自动化验证，再用两台 Windows 设备验证真实广播和防火墙行为。

### M3.2：配对、信任与 Brain 目录

- 实现双端短码/指纹确认、受信节点列表、撤销和重新配对。
- 每个实例可承载默认 Brain；节点能发现一个或多个 Brain，并显示其在线状态和能力。
- 节点间产品 API 使用加密和双向身份校验；OpenCode 仍只绑定 loopback。
- 验证伪造广播、重放配对、已撤销节点和版本不兼容请求被拒绝。

### M3.3：单 Brain 的分布式任务闭环

- Brain 创建任务并选择受信执行节点；执行节点本机确认项目和模型额度。
- 远端人类成员能够接受、审批、补充、停止、查看差异和验收。
- 执行日志、人工操作和产物摘要回到归属 Brain；敏感项目文件不因节点发现自动复制。
- 两位真人在两台 Windows 设备完成一次真实编程任务。

### M3.4：最小多 Brain 委派

- 两个 Brain 同时被发现并各自保留身份和本地任务。
- Brain A 可把任务执行委派给 Brain B 管理的执行节点，A 仍是任务归属方。
- 断网重连后使用幂等事件和租约避免重复执行；归属 Brain 离线时明确暂停。
- 验证两个 Brain 各自发起任务并相互提供执行能力，不把切换账号或同一数据库的两个客户端算作通过。

## 非功能要求

- **安全**：发现信息最小化；首次信任有人确认；节点间加密、双向认证、消息防重放；支持撤销节点。
- **隐私**：不广播用户、企业、项目、模型和任务信息；不自动上传工作区。
- **可靠性**：重复消息不重复执行；断线可恢复事件读取；离线状态可见且不自动转移所有权。
- **在线判定**：连续 30 秒没有通过签名校验的发现心跳即显示离线，120 秒后从附近列表移除；恢复心跳自动回到在线。此展示状态不能代替后续任务执行租约。
- **维护成本**：沿用现有 Node.js、SQLite、React 和 Tauri；不部署必需云服务，不实现共识数据库。
- **兼容性**：协议带版本号和能力协商；不兼容节点可被发现，但不能进入任务协作。

## 主要故障与处理

| 故障                   | MVP 行为                                                    |
| ---------------------- | ----------------------------------------------------------- |
| mDNS 单向失效          | 自动使用 UDP 查询/单播回复回退，之后仍完成签名握手          |
| 两种局域网发现均被阻断 | 显示诊断，并允许已知节点地址作为发现种子                    |
| 恶意设备伪造发现广播   | 未配对前只显示最小元数据；业务请求必须通过密钥校验          |
| Brain 离线             | 其任务暂停写入；缓存事件可查看，不自动选主或接管            |
| 同一任务被重复委派     | 归属 Brain ID、任务 ID、幂等键和执行租约共同去重            |
| 执行节点中途离线       | 租约到期后由归属 Brain 和人类决定是否重新执行               |
| 受信节点后来不可信     | 撤销设备身份；后续请求拒绝，既有副作用不承诺自动回滚        |
| 两个 Brain 同时存在    | 各自拥有自己的任务；跨 Brain 只交换受约束消息，不共写数据库 |

## 影响

### 正面

- 产品从单机任务客户端演进为本地优先的协作网络，个人与企业使用同一抽象。
- 多 Brain 不依赖中心云服务，也不要求所有节点共享文件系统或数据库。
- OpenCode 和模型凭据继续封装在执行节点内部，符合薄适配层约束。

### 代价

- Windows 防火墙、mDNS/UDP 兼容性、设备身份、撤销和断线恢复都成为必须真实验证的产品能力。
- 当前 loopback 应用 API 需要拆出受限的节点间协议层，现有安装包不能直接宣称支持该能力。
- 多 Brain 的离线接管、跨网络发现和企业策略会形成后续里程碑，MVP 只保证明确暂停和人工恢复。

## 未采用方案

- **单主机加远程访客**：无法表达节点平等、自发现和多个 Brain，已被产品方向否决。
- **所有节点共写一个数据库**：局域网文件共享和 SQLite 多写者风险高，故障边界不清楚。
- **一开始实现 Raft 或完整多主复制**：超出一人 MVP 的开发和运维成本，且当前任务单写者模型已经能验证核心体验。
- **直接暴露 OpenCode 服务**：会泄漏过多引擎能力和凭据边界，不符合产品安全约束。
- **必须依赖中心云服务发现**：增加成本并削弱个人本地场景；跨网需求以后以兼容协议补充。

## 验收要求

只有在两台真实 Windows 设备上完成“自动发现 → 双端配对 → 发现 Brain → 分配执行节点 → 人工审批 → 查看差异与产物 → 验收”，才能把单 Brain 跨设备协作标记完成。只有在两个独立 Brain 间完成任务委派、断线重连和去重验证，才能把多 Brain MVP 标记完成。
