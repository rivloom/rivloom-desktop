# ADR-0010：任务图与执行过程中的 Node 转交

## 状态

2026-09-09，已实现并通过隔离验证，交付记录见[实施计划](../plans/2026-09-09-collaborative-task-flow-implementation.md)。目录/工具登记、认证查询、持久步骤与执行意图、真实只读规划、依赖并行、检查点转交、原会话图和 `@`/`@@` 均已接入。旧 `a152322c` 安装包不包含此次功能。单一 `collaboration-v1` 能力保持旧节点握手兼容，旧节点不参与新工作流。任务/文件访问仍使用原归属和认证通道；未确认停止或不确定接受的执行不重派。

固定 OpenCode 1.18.25 的 `format: json_schema` 消息持久化缺陷已用真实引擎复现（[上游 40169](https://github.com/anomalyco/opencode/issues/40169)），因此 schema 放入任务提示，完整最终 JSON 经类型、大小和 DAG 校验后绑定 session/run/attempt；无有效结果即失败，不降级为伪造计划。独立停稳检查只覆盖可确认的同步工具和受限媒体命令，其他外部脚本不能据模型声明自动转交。300 项逻辑、13 项协议、12 项双服务检查通过，含目标重启保持原执行/会话及原工作流确认停止。下文“当前代码事实”和难度表保留为开发前审查依据，缺口描述不代表此轮最终实现状态。

## 用户场景

用户发出一个任务，复杂任务自动展示步骤卡与依赖连线。步骤可交给不同 Node，存在并行和汇合。另一个场景是视频生成误指定轻薄本：轻薄本检查到本机不适合，找到能处理的 GPU 节点，交接任务；发起方原会话自动出现“轻薄本 → GPU”的执行记录与转交原因。

同一步骤的机器转交与不同步骤的前后依赖是两种关系。用户保持一个原任务入口，可查看各段执行、素材与最终结果。

**用户补充：转交不限硬件。** 所需素材、文档、工具或访问条件只在 Node B 时，Node A 也可能需要委托 B 或转交。用户提出“谁有文档 abc”应作为极轻量协作查询，不创建正式任务：优先查询 Brain 已富集的信息，不确定时由 Brain 询问其他 Node。下文新增资源发现方案；首版切入口不再限定 GPU，先建设可复用的查询和定位能力。

**最新四项修订：** 工作目录资源上报始于配对后用户选定目录；系统先分析和拆解用户请求再判定是否展示任务图，不以用户是否 `@` 指定机器为条件；`@Node` 表示首选，`@@Node` 表示锁定；用户明确认可规划后条件满足即执行，保留危险操作审批及队列达到 10 的追加确认。具体产品行为和可发现性交互见 [开发前确认稿](../plans/2026-09-09-collaborative-task-flow-brief.md)。

## 结论与规模

可实现，已有协议、队列、文件和执行记录可复用；整体为中等偏上的产品/调度功能。界面本身较容易，主要成本是运行中停止与交接的一致性、能力检测及恢复。开始前环境检查发现不适合的场景明显比运行到一半迁移容易。任意进程和 GPU 内存状态的透明迁移不适合作为首版承诺。

| 范围 | 相对难度 | 当前基础与缺口 |
| --- | --- | --- |
| 卡片、依赖线、转交历史实时展示 | 较低到中等 | 有会话、远程状态和执行历史；缺稳定逻辑步骤与转交事件 |
| 硬件不匹配时选择合格 Node | 中等 | 有硬件/显存要求与筛选；缺文本需求结构化和软件能力确认 |
| 检查环境后、重任务开始前转交 | 中等 | 可复用入队、附件、执行记录；需目标绑定的转交协议 |
| 已开始执行后的停止、产物交接与恢复 | 较高 | 有停止确认和文件续传；缺持久交接事务、代次约束与可续作上下文 |
| 任意任务自动拆解、动态并行和依赖执行 | 较高 | 当前没有工作流 DAG 引擎；需版本、依赖、失败与取消传播 |
| 正在计算的任意视频任务无损热迁移 | 很高且依赖工具 | 现有系统没有进程/显存迁移；只能按工具支持的检查点设计 |

这些是代码审查后的相对判断，不是已测得的工期。应先完成一个具体视频执行器的真实跨机验证，再估计可推广范围。

## 当前代码事实

- `server/worker-resources.ts` 的 `workerMatchesTask`、`rankWorkers` 支持操作系统、架构、CPU 核心、内存、GPU 和总显存门槛，并根据新鲜报告与空闲槽筛选。`WorkerRegistration` 尚无视频工具、模型文件或运行环境能力描述；当前显存门槛也不等于已验证可用显存和实际可运行性。
- `src/conversation-workspace.tsx` 的自动分配提交仍提供空 `requirements`；当前不会自动把自然语言视频要求转换成资源约束。
- `server/brain-tasks.ts` 已有一个 Brain Task 多次 Execution 的持久历史，按 executionID/attempt/sequence 隔离状态；`requeueExecution` 仅允许 executionSequence 为 0 的明确拒绝、过期或取消，接受后结果未知保持等待。
- `server/node-network.ts` 的 `createTaskForNode` 是固定目标 remote-task，`createScheduledTask` 是 BrainTask。直接指定的任务不会天然拥有统一的多机执行历史，两条路径需要适配到新增逻辑步骤，而非直接修改旧邀请的 targetNodeID。
- `server/task-service.ts` 的 `stopTask` 请求引擎停止并检查 idle，保留消息及产物；停止未确认转为 interrupted。该确认需要视频工具保证外部进程也已结束，不能仅凭会话 idle 宣称 GPU 工作停稳。
- `server/task-files.ts` 已有任务绑定、完整文件验证、加密传输相关存储及重启续传；中间产物仍需明确选择、打包和重新绑定。现有能力不等于同步整个工作目录或搬运模型权重。
- 原协作记录限制归属、参与方和认证路由。A 与 B 配对、B 与 C 配对不意味着 A 与 C 自动互信；执行器的转交请求必须经原协调方确认路由与该任务的授权范围。
- 当前 `brain-directory-request/response` 交换 Brain 拓扑、Worker 报告、资料名片与队列，尚无用户文件目录、语义检索或跨机问询。已有 task-files 接口按任务/参与方授权，不可直接将其改为全盘搜索接口。

## 建议架构（待评审）

```mermaid
flowchart LR
  U[发起方：原任务与任务图] <--> O[原任务协调方]
  O <--> A[轻薄本：环境检查与交接]
  A -->|能力不匹配：提交结构化转交请求| O
  O -->|目标确认、输入完整、原执行已停稳| B[GPU Node：新的执行段]
  B -->|进度与结果| O
```

这里 O 是原 Task 的协调方：Brain 任务沿原 Master，直接任务需新增由原发起方持有的逻辑执行记录。A 可以检测问题、建议候选并发起转交；O 负责串行提交转交决定。用户界面的执行关系仍展示 A → B，不暴露后台消息绕行细节。

### 建议一：任务、步骤、执行段分开

稳定的原任务 ID 下包含逻辑步骤；每一步可有多个历史执行段。依赖连接步骤，转交连接同一步骤的两个执行段。每个执行段沿用独立执行标识，原协调方持久保存当前有效代次。旧任务通过适配保持原状态和归属，不进行批量迁移。

先实现单步骤的多机器执行历史，也可为后续 DAG 提供基础。卡片由已保存的真实事件更新，重启后可重建；“准备转交”“传输中”“目标已入队”“执行中”分别展示，不提前伪造成功。

### 建议二：Agent 提出转交，调度层执行交接

给 Agent 提供受控、结构化的能力查询与转交入口，包含原因、资源/工具要求、目标建议和待交接产物。环境探测与对端确认决定可运行性，不仅依赖模型文字判断。

对视频至少检查所选执行器可用、所需模型就绪、GPU/显存、磁盘以及输入兼容。能力证明有时效；静态能力合格但繁忙的机器可按原队列等待，不能因没有空闲槽就误判不支持。未知能力先探测，不伪造已满足。

### 建议三：转交是可恢复的事务

原协调方持久保存唯一 handoffID、逻辑步骤、旧/新执行代次、来源、目标、原因、输入清单及阶段。推荐阶段为请求、探测目标、冻结原执行、确认停稳、准备完整输入、提交目标队列、目标确认接收、开始新执行。

目标的探测/材料暂存不授予执行权限。旧执行已停稳、材料完整、目标确认后才能启用新执行；请求和 ACK 丢失均用同一 handoffID 重放。旧代次晚到结果保留为历史，不覆盖当前结果。停止状态未知时保留等待，不因网络超时同时启动第二份工作。

还需处理：目标拒绝、文件校验失败、取消与转交竞争、协调方/两端分别重启、目标能力变化和转交环路。每步保存已尝试节点和有界转交次数，防止 A → B → A 无限循环。

### 建议四：交接明确的工作内容

首版交接任务要求、输入素材、结构化进度、可复用的中间结果和执行参数。目标可以从最近的业务步骤继续；新机器使用自己的工具环境。若执行器支持检查点，可增加其专用导入/恢复适配；否则明确从该计算步骤重新开始，不能称为无损续跑。

不默认搬运整个磁盘目录、凭据或模型权重。大模型应提前部署；超过当前附件范围的视频素材需另行设计文件通道，不能因已支持 200 MiB 就声称所有视频工程均能交接。

### 建议五：自动转交不增加逐次人工验收

用户已确定新增任务使用 `@Node` 表示首选、`@@Node` 表示锁定；无前缀也先分析步骤并可自动选择机器。启用允许转交的任务可在既定协作范围内自动完成转交；锁定限制执行所在机器，不通过远端子任务绕开，仍可查询/获取资料。旧固定目标任务保留语义。目标只在轻薄本的配对范围、无法经原协调方现有认证路由访问时，需另行设计按任务授权的委托与回执；不扩大为全网默认互信。

现有危险工具审批和队列达到 10 的发起方确认继续生效；转交目标变化不能沿用另一台机器的队列确认。队列提醒不变成每次转交必弹的审批。

## 建议分期

1. 建设下述轻量资源发现：本机可发现资料目录、Brain 索引、询问/回应、缓存与结果来源。覆盖“谁有 abc”“谁有某素材”“谁能提供某工具”，不进入正式任务队列。
2. 单步骤、单次转交、现有认证协作范围，同时覆盖资料在 B 和 GPU 在 B。实现稳定任务历史、转交协议与实时卡片；验证取消、重启、重复请求和结果归属。明确区分取资料、委托子步骤和转交剩余任务。
3. 加入执行中停稳、摘要/产物交接与从业务步骤继续；以一个具体视频执行器验证外部 GPU 进程真正停止，以及中间结果是否可复用。
4. 加入多步骤 DAG：显式输入/产物、依赖完成门槛、并行和汇合、失败阻塞、取消传播与重跑版本；之后再让 Agent 动态扩展图。

## 扩展建议：先问 Brain，再按需询问 Node

### 资源在哪里，与任务在哪里执行分开决定

资料存在于 B 并不只有一种处理方式：

- 素材小、可传输且 A 的执行环境合适：取回所需文件或片段，由 A 继续。
- 资料很多、需就地访问或工具只在 B：委托 B 完成明确的子步骤，只回传结果。
- 剩余工作整体依赖 B 的资源：按前述协议转交原步骤，记录 A → B。

决策依据包括数据位置、传输规模、工具与模型、有效访问条件、硬件、当前负载和用户目标策略。不能仅按 GPU 或机器性能排序，也不能因为有文档就无条件搬走整个任务。

### 两条通道

**发现查询**使用独立 requestID、期限和有限回应，不创建 Task、Execution、模型会话或 Node 执行队列项，不触发 10 个任务的排队提醒。它仍消耗少量 I/O 和网络，因此需要独立并发/速率/结果数限制。文件存在性、名称/标签匹配和已建索引查询可由程序完成，不要求每个 Node 都调用一次模型。

**正式工作**继续沿原任务/执行/队列通道。任意 shell 操作、生成内容、读取并分析大量文件或超过查询预算的工作不能借“轻量查询”绕过队列。语义索引的构建与昂贵内容理解需独立控制成本；首版可用名称、别名、标签与普通全文索引，不把全部查询都升级成 Agent 工作。

### 查询与富集流程

用户进一步明确：机器配对后，Node 主动登记已配置工作目录的情况及基础软件/硬件信息，之后周期更新，Brain 汇总这些偏静态资料，再据此开展任务转交。建议采用此先后顺序，并按以下策略控制更新成本和信息时效。

#### 主动登记与持续更新

| 信息类别 | Brain 保存的主要信息 | 更新方式 |
| --- | --- | --- |
| 工作目录与资料 | 工作区标识、用途、可发现资源的 ID/名称/相对位置、类型、大小、更新时间、标签与版本 | 首次连接分批索引，变化合并推送，周期校对 |
| 软件与模型 | 与工作相关的工具、版本、探测结果、已就绪模型/工作流及支持操作 | 初次探测，配置变化触发，低频复查 |
| 硬件 | 系统、架构、CPU、内存、GPU、显存等能力 | 初次连接与启动采集，配置变化或低频复查 |
| 当前可用性 | 在线、暂停、执行占用、等待数量、实时资源余量 | 复用现有动态报告，独立于静态目录时效 |

- Node 配对后先由用户选择工作目录，选择完成且认证通道可用后，才开始该目录的分批索引并发出带版本号的资料/能力快照；未选择目录不推测扫描位置。首版以其中可发现的元数据为主，正文按需读取。目录配置不默认触发全文上传，也不自动同步密钥、凭据、缓存和依赖树。目录移除后对应资源退出可发现范围。
- 扫描和工具探测在本机后台分批执行，不阻塞启动、输入和已有任务。已安装软件清单只覆盖有用的工作能力，探测返回版本、最后检查时间以及已验证/未知/不可用，不用软件名字替代实际可执行性。
- 文件变更合并为增量，包含增加、修改、删除和重命名；完整快照分段提交并标明扫描完成，索引尚未完成时不能将未列出的文件视为不存在。
- 周期性告知主要检查版本和摘要；没有变化无需重复发送整个目录。文件监听可能漏事件，因此保留低频重扫校对，按目录规模与活跃程度调整。避免每次心跳遍历文件或运行软件探测。
- 重连先交换已知版本并补增量；缺口无法补齐时重新同步快照。Brain 记录每条信息的拥有者、目录版本、内容版本和最后确认时间，忽略乱序旧报告。一个 Node 的目录不会被另一 Node 无条件覆盖。
- 静态资源目录可比在线状态保留更久；离线后仍能说“最后确认 abc 在 B”，但 B 暂不能执行。撤销配对或共享范围后，查询立即按新范围过滤并使相关缓存失效。
- 当前代码已上报配置执行项目的 ID/名称和硬件/负载，但没有工作目录文件索引或软件能力清单；需新增独立协商能力/消息，不能直接扩展现有严格校验的 WorkerRegistration 字段。

Brain 的汇总可先采用结构化数据库与索引，不要求每轮由模型阅读全目录。任务到来时，从这些记录选候选；不确定或过期时再执行有界查询。此后流程仍为：**找到候选 → 对端现场确认资料/工具可用 → 决定取资料、委托或转交 → 走持久交接协议**。目录解决“可能谁能做”，不替代接收、停止确认和输入完整性。

#### 有请求时按需确认

1. 各 Node 为明确开放发现的资料范围维护本机索引，增量发布允许共享的条目元数据或集合摘要：资源 ID、名称/别名、类型、简短标签、版本/更新时间、可用操作。绝对路径、完整原文和凭据不默认同步到 Brain。
2. A 向其原协调 Brain 发起一个查询。Brain 查当前请求方可见的索引，返回带来源、确认时间和匹配理由的候选。请求“最新版本”时需再验证，不能将旧缓存当成最新事实。
3. 无命中、版本不确定、目录过期或候选不足时，Brain 先向可能持有的 Node 并行询问；无法缩小范围时向该请求有权查询的、可达的协作 Node 各问一次。
4. Node 查本地索引并对候选确认存在性/可见性，返回受限结果。查询沿认证通道单次分发，不使用局域网明文广播或各 Node 递归转发。原请求方身份与查询范围必须可验证，不只检查消息来自 Brain。
5. Brain 聚合、按资源版本/内容标识去重，保留各份实际副本位置，将授权范围内的结果短期缓存。缓存键包含可见范围；删除、权限撤销、版本更新和 Node 离线需要失效或标为待确认。
6. A 得到“B 有 abc、C 有相关版本、两台未响应”等真实结果，再决定取回、就地子任务或整体转交。正式获取和执行前再次检查权限、资源版本与目标状态。

先返回可用结果，其他回应按期限补齐；请求方取消后停止追加工作。未响应/离线与“已查过但没有”区分，部分回复不能宣称所有 Node 都没有。相同请求重试复用查询 ID，限制扇出与跳数，防止广播风暴和循环问询。

### UI 表达

“正在寻找 abc · 已询问 3 台”“在 Node B 找到 · 刚确认”作为原会话内轻量、可展开的协作记录。普通存在性问询不占历史会话，不为每个被询问 Node 生成正式任务卡。查询记录可展开查看来源、未回复节点和选择原因；实际子步骤、委托或执行转交才形成相应任务卡与关系线。

### 当前可行性与验证

有界的资料发现/询问难度为中等，低于运行中的可靠迁移。可复用 Node 身份、加密请求回应、能力协商及连接状态；需新建本地资料索引、Brain 目录、按请求方过滤、缓存失效与扇出协议。首版先在现有可认证协作范围内实现，跨 Brain 或只由中间节点配对的搜索另需范围与委托设计。

最少验证：目录命中/未命中/过期、同名不同版本、增量删除、文件移动、权限撤销、不同请求方缓存隔离、部分 Node 离线、重复/超时/取消查询、结果上限与重复扇出，以及查询期间零正式 Task/Execution/模型会话创建。主动上报还需覆盖目录配置变更、首次扫描中断、重连补版本、乱序增量、监听漏报后的校对，以及大型目录对启动/会话响应的影响。检索到文档并不自动授权取回原文或执行其中内容。

## 取舍与验证门槛

不采用“轻薄本直接复制任务并发给 GPU”作为通用实现：虽然演示快，但会分裂原会话、结果归属及重试控制。也不通过放开现有 `requeueExecution` 条件实现运行中迁移：它没有完成停止和材料交接证明。

复用 SQLite、现有加密 Node 通道、文件机制和前端状态更新；当前规模无需新增外部消息系统。新增协调方逻辑会增加协议和恢复测试成本，协调方离线时首版允许等待；高可用迁移不混入第一阶段。

最少需要覆盖：轻薄本无 GPU、GPU 有硬件但缺工具/模型、目标繁忙、目标只与中间节点配对、200 MiB 文件中断恢复、停机确认丢失、交接 ACK 丢失、三方重启、旧结果晚到、提交方取消、转交循环和队列超阈值。真实视频执行器和两台机器的结果验证是最终可用性证据；已有文字任务/隔离协议检查不能替代。
