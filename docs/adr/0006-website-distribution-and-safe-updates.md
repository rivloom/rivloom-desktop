# ADR-0006：官网分发与安全更新

## 状态

**分阶段实施中，2026-09-05。** 用户已确认两个独立源码仓库、`rivloom.com` 官网和 Cloudflare 同时服务中国大陆与海外，官网首版与基础 CI 已开始；正式签名、公开发行和安全更新仍待后续完成。本文不代表更新功能已实现或网站已部署，不改变 M3.5 的当前实施和验收状态。

依据为用户提供的[分享对话](https://chatgpt.com/share/6a9b8fce-808c-83ee-9aab-13b5c746e4ca)及现有仓库。本文提炼其中可用方向，并补充现有 Node/Brain、安装与恢复边界；详细标准见[发布与更新指南](../RELEASING.md)，阶段状态以[里程碑基线](../MILESTONES.md)为准。

## 背景

当前产品是 Tauri Windows x64 客户端，随包携带锁定的 Node.js、官方 OpenCode、本地服务和前端。已有未签名内测安装包及有限安装/升级证据；本轮已补充本地验证的 Windows 测试与内部 Preview 候选工作流，尚无云端运行成功记录、完整自动更新或干净 Windows 发行矩阵。

节点之间存在稳定身份、持久信任、Brain/Task/Execution 归属和执行中的资源占用。分发新安装包既要确保来源，也要确保安装时机与数据恢复不会重复执行任务。官网、文件下载和运行中的节点协作不应共用同一服务职责。

## 建议方向

### 1. 官网、安装产物与源码分别管理

- 2026-09-05 用户已建立两个独立源码仓库：桌面 `rivloom/rivloom-desktop` / `C:\project\rivloom-opencode`，官网 `rivloom/rivloom-website` / `C:\project\rivloom-website`；后者已克隆，不在桌面目录内嵌套新仓库。官网下载元数据由桌面发行记录提供；R2 等对象存储承载安装包时无需第三个源码仓库。具体检查点见 [官网、CI/CD 与更新实施计划](../plans/2026-09-05-website-ci-cd-and-updates.md)。仓库落地不等于后续下载与更新流程已实施。
- 官网采用静态站点，负责产品说明、下载入口、版本说明、支持信息和已知限制；网站更新不要求重建桌面包。
- 官网使用用户确认的 `rivloom.com` 与 Cloudflare；下载/更新子域名和存储仍待设置，按实际 DNS、HTTPS 与下载验证确认可用性。
- 版本安装包可放对象存储/CDN（R2 为候选），或独立公开分发仓库的 Releases；GitHub Releases 是否适用由可达性、预算和运营需求决定。
- 私有源码仓库不作为需要客户端持有仓库令牌的公共下载源。不得将源码仓库 token、上传凭据或签名私钥嵌入客户端；公开分发仓库只发布经过核对的产物和元数据。

### 2. 使用官方更新能力，区分各类校验

- 优先接入[官方 Tauri updater](https://v2.tauri.app/plugin/updater/)，使用其签名校验和 HTTPS 更新源；具体插件、权限、公钥和产物配置须在实施时核对并验证。
- SHA-256 用于核对文件一致性；updater 签名验证更新产物的签名来源；Windows Authenticode 用于 Windows 代码签名和发布者识别。三者作用不同，不能相互替代，也不承诺消除所有系统信誉提示。
- 私钥由受控发布环境保管，客户端仅持有对应公钥。签名策略和密钥恢复/轮换须在首次更新发布前形成可验证操作记录。
- 桌面、业务服务、前端、Node/OpenCode 和必要声明按锁定版本整包发布；不让客户端独立自动追踪上游引擎 latest。
- 现有 `com.rivloom.conversationpreview` 是独立预览应用，不能直接视为正式客户端的 beta 频道；正式测试频道需另行定义版本、更新源和数据兼容规则。

### 3. 不可变版本与可切换频道

- 每个发布版本的安装包、签名及校验记录使用不可变地址和唯一版本标识；修复后产生新版本，不覆盖已经交付的同版本文件。
- 先上传完整产物并验证下载、签名和安装，再更新频道指针/更新清单；官网下载入口与更新源指向同一已核对版本。
- 版本产物使用适合长期缓存的策略，频道清单使用可及时更新的缓存策略。频道清单只是发现入口，不能代替产物签名校验。
- 发布记录关联源码提交、锁定依赖、构建环境、产物摘要、签名状态、验证结果和发布说明，支持追溯与撤回。

### 4. 安全升级属于 M2

- 安装前停止新的执行准入，检查本机和远端已承诺工作，持久化状态，并通过既有生命周期流程退出自有服务和引擎；不能直接覆盖仍被占用的 runtime。
- 升级保持 Node 身份、DPAPI 当前用户绑定、信任、Brain、Task/Execution 和用户配置；迁移须有备份/恢复及失败处理证据，不删除历史或用新身份掩盖失败。
- review、interrupted 和结果未知的执行仍遵守现有占槽与恢复规则。不得因更新、超时或断线自动重派可能已经执行的任务，也不得将下载完成当作安装成功。
- Master 当前没有 HA。升级 Master 可能暂停其 Brain 调度；应向用户说明影响并协调更新时间，不能宣称滚动更新天然无中断。
- 自动检查、下载与安装分开表达，安装重启应在可确认的安全时机执行；具体交互和自动化程度由实施方案确定。

### 5. 混合版本兼容与故障处理

- 沿用现有 `protocolVersion=1` 与 capabilities 协商，分别管理应用版本、协议版本和持久数据格式版本；不新增没有实现依据的 `skillProtocolVersion`。
- 新能力只对支持方发送；旧方未提供的队列状态显示未知，未确认的远端操作不得显示同步成功。不兼容时明确限制相关协作，不承诺任意版本互通。
- 每次发布声明并验证所支持的混合版本组合、升级顺序和数据迁移范围；是否需要提高协议版本须根据实际破坏性变更判断。
- 发现坏版本时先暂停该版本分发和更新推荐，保留证据，再提供更高版本修复。不得默认把已迁移数据交给旧程序，也不把回切频道指针称为已安装客户端自动回退。

### 6. 官网与发布运营属于 M5

M5 汇总目标版本的官网、公开产物、CI 发布、发布说明、支持渠道、来源与隐私说明、运行时许可证及已知限制。CI 将构建/验证、签名、上传和切换频道分成可核对步骤；真实外部发布、域名和证书使用在实施阶段根据具体交付范围处理。本次文档整理不执行网络部署或购买。

## 替代方案与取舍

| 方案 | 取舍 |
| --- | --- |
| 先官网手工下载，再接 updater | 可降低首轮实施量；仍须不可变版本、来源校验和升级说明，不能称自动更新已完成。 |
| 独立公开 Releases 分发 | 减少存储运营；需核对目标用户可达性，私有源码与公开产物保持分离。 |
| 对象存储/CDN 分发 | 可独立控制域名和缓存；增加权限、缓存、发布原子性及成本管理。 |
| 自建通用更新服务或脚本替换程序 | 暂不优先，现有官方 updater 更贴合桌面技术栈；避免扩大服务端维护和安装权限范围。 |

## 非功能目标与完成判断

目标是发布来源可验证、版本可追溯、失败可解释、数据与归属可恢复，以及公开分发不泄露私有源码和凭据。网络中断、签名失败、磁盘不足、安装中断、混合版本、迁移失败和占槽任务均须有明确结果；通过记录按目标版本归档，不复用旧包证据冒充新发布验收。

具体 M2/M5 分期、检查清单和未覆盖项见[发布与更新指南](../RELEASING.md)。接受文档中的路线记录不构成已实现、已验证或已公开发行声明。
