# ADR-0003：设备信任与 AI 审批分层

## 状态

已接受。产品负责人于 2026-09-01 明确：完成双向配对的设备已经建立业务信任，受信设备发来的任务不应再次要求逐任务接受；AI 在执行电脑上的文件和命令权限由另一套本机审批策略管理。

## 决策

1. 只有完成双向指纹确认、仍未撤销且加密通道有效的节点可以发送任务。任务通过该边界后，接收节点立即接受，不再提供“每项任务确认”或节点白名单的第二层邀请审批。
2. 本机所有者仍可关闭执行能力、选择专用项目和模型、停止任务或撤销设备信任。关闭能力时已接收的新任务等待，不创建 OpenCode 会话；重新开启后再按本机能力执行。撤销信任会阻止后续消息并停止关联执行。
3. 每项本机任务在创建时锁定一种 AI 审批模式：
   - **请求批准**：读取普通项目文件和搜索自动允许；修改、命令和联网工具请求指定审批人决定。
   - **帮我批准**：项目内修改和命令自动允许；联网工具仍请求批准。
   - **允许任何操作**：受支持的文件、命令和联网工具自动允许，并允许访问项目外目录。它必须显式选择并显示高风险警告。
4. 三种模式都继续拒绝读取 `.env`、私钥、OpenCode 认证文件等敏感内容，也继续禁用子代理和技能加载。这里的“允许任何操作”只表示 Rivloom 当前开放的文件、命令、联网与目录范围，不取消凭据保护或引擎边界。
5. 权限通过 OpenCode 1.18.25 官方 `session.create({ permission })` 规则传入。Rivloom 不修改 OpenCode，不实现工具执行器，也不模拟 Agent 循环。
6. 任务的审批模式创建后保持不变；修改节点默认策略影响以后收到的跨节点任务，以及选择“跟随本机设置”的新本机任务。本机发起时可明确覆盖当前任务的模式。已有任务和会话不会被静默扩大权限。
7. 升级旧配置时，原“自动调用”保留开启但改用“请求批准”；原“有限调用”和“每项确认”关闭执行能力，要求本机所有者按新语义重新开启，避免升级时静默扩大设备或模型调用范围。
8. 归属 Brain 可以通过现有认证加密任务通道处理执行中的具体权限请求、AI 提问和停止操作。控制消息必须携带任务路由、唯一控制 ID 和预期执行序号；执行节点只在来源仍受信、任务仍唯一绑定且请求仍有效时调用官方 OpenCode SDK。
9. 执行节点只回传处理人工介入所需的最小快照。审批 metadata 一律移除；文本先执行敏感信息脱敏，本机项目根目录若出现则替换为 `<project>`。本机项目 ID、模型、任务 ID、凭据和 OpenCode 通用接口不进入节点消息。
10. 远程停止沿用本机停止语义：中止官方会话并拒绝残留审批/提问，不回滚已经完成的修改。拒绝和停止都必须由界面明确触发，不因网络重试重复执行；控制 ID 在执行节点持久化去重。
11. 归属 Brain 可发送补充要求。执行节点先按本机停止语义处理仍在运行的会话，再在同一 OpenCode 会话追加要求并继续；每个任务同时只接受一项远程操作，避免补充、审批和验收竞争。
12. 执行节点只回传 OpenCode 官方会话接口明确给出的差异，并在发送前脱敏、替换项目根目录和限制消息大小。Rivloom 不扫描文件夹、不建立快照或内容哈希；官方接口无差异时，归属 Brain 必须看到明确限制。
13. 归属 Brain 只能在远端任务处于 `review` 时提交带核对说明的验收。执行节点使用本机业务任务的指定验收人完成状态转换；验收不提交、推送或部署。

## 产品含义

- “信任设备”回答谁可以把任务交给本机。
- “开启执行能力”回答本机是否愿意接活，以及使用哪个本地项目和模型。
- “AI 审批模式”回答 OpenCode 执行过程中哪些动作需要人批准。

三者不能再合并成一个“自动/有限/每项确认”的调用下拉框。若用户不再信任另一台设备，应撤销设备信任；若只想暂停接活，应关闭本机执行能力；若想调整 AI 自主程度，应选择审批模式。

## 当前范围

受信任务自动接收、审批模式持久化、本机会话权限，以及跨设备展示和处理具体审批请求、AI 提问、停止、补充要求、官方差异与验收已经落地。用户已完成真实 DeepSeek 的单人双机请求批准、文件生成、同会话补充和最终验收，产品负责人据此接受 M3.3 的 MVP 范围完成。停止、另外两种审批、撤销信任、异常断网及两真人角色回归继续保留为后续优化，不阻塞 M3.4 产品讨论。
