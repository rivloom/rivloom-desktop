## 当前工作顺序

1. 下一会话从 M3.4 产品讨论开始，先定义 Brain、节点、人、任务、模型/算力和项目资源之间的关系，以及个人与企业场景的最小共同模型。
2. 不沿用未经确认的“每个节点一个 Brain”或“Brain A 委派给 Brain B”等历史假设；先形成可评审的场景、角色和边界，再更新 ADR 与实施计划，之后才写代码。
3. M3.3 剩余物理回归和 Windows 防火墙安装体验进入后续优化清单，不阻塞 M3.4 讨论。
4. M2 的正式发行完善其余部分暂缓，不因现有安装包而宣称商业发行已经完成。

## M1 真实验证结果

1. 用户在本机“模型与额度”页面保存 DeepSeek Key，界面不回显完整 Key；真实连接测试通过且没有自动重试。
2. `deepseek/deepseek-v4-flash` 在没有 `.git` 的专用普通文件夹执行固定 slugify 编程任务。
3. 操作者拒绝一次计划外目录列举，补充约束后继续；随后分别批准预期文件编辑和 `node --test slugify.test.mjs`。
4. 独立核对确认只存在两个预期文件、测试文件未改、1 项测试通过且 0 项失败，任务最终完成验收。
5. OpenCode 官方 `session.diff` 返回空数组；界面如实显示无会话差异，没有使用 Rivloom 文件快照或内容哈希兜底。
6. 报告只记录模型标识、会话 ID、操作分类与结果，不记录 Key、完整回复或用户项目内容。

项目文件夹不要求 Git。Rivloom 不为任务建立文件快照或内容哈希；若 OpenCode 官方会话接口返回差异则展示，否则由验收人直接检查本地文件和测试记录。

## M3.3 当前已知事实

- 可信节点之间已经可以发送加密协作任务。
- 受信节点发来的任务会自动接收；本机可关闭执行能力或预设项目和模型。
- AI 操作审批已支持“请求批准 / 帮我批准 / 允许任何操作”，并通过官方 OpenCode 会话权限接口传入。
- 发起端已经能收到有序执行状态和最终摘要。
- 发起端已经能在加密任务通道上批准/拒绝具体操作、回答 AI 提问、停止远端任务、补充要求并继续同一 OpenCode 会话，以及提交最终验收；控制会校验设备信任、任务路由、唯一控制 ID 和执行序号。
- 审批和提问快照不含本机项目 ID、模型、凭据或 metadata，项目根目录若出现则显示为 `<project>`。
- 发起端可查看限长、脱敏的 OpenCode 官方会话差异；官方接口无差异时明确提示由执行机参与者本地核对，不扫描或哈希文件夹。
- 安全通道已覆盖单边会话丢失：较大 Node ID 发送签名恢复请求，由确定的较小 Node ID 重建通道，避免双方并发握手。
- 2026-09-02，Win11 `192.168.5.20` 与当前开发机 `192.168.5.33` 已用真实 DeepSeek 和普通文件夹完成单人双机闭环：可信任务自动接收、远程一次性批准文件写入、生成文件、补充要求后续跑同一 OpenCode 会话、本地核对结果和归属端最终验收均通过。
- 本次发现 `5.33` 上随包 `node.exe` 的 TCP/UDP 入站规则虽已启用但 `Action=Block`；改为 Private Profile 的 Allow 后，`5.20 → 5.33` TCP 探测和自动发现恢复。安装器尚未可靠创建、检测或修复规则，这是下一项实现工作。
- 产品功能已形成“发送 → 自动执行 → 人工介入 → 补充 → 查看结果 → 验收”闭环；单人双机核心体验已验收，M3.3 的 MVP 范围完成。
- 远程停止、另外两种审批、撤销信任、异常断网恢复、两真人角色回归及防火墙安装体验保留为明确的后续优化，不作为当前推进阻塞项。
- 当前“单个可复用项目和模型”的实现是 M3.3 已验收切片；它不预先决定 M3.4 的 Brain 与资源模型。

## 暂停与延后项

- M3.4 可以开始产品讨论，但定义确认前不进入实现。
- 不用旧的 30 分钟准备租约流程。
- 不优先开发 ChatGPT 登录、更多模型供应商、自动更新或正式发行签名。
- 不把尚未完成的两真人、停止/自动审批/撤销及防火墙回归描述成已验证；它们已记录为后续优化。
