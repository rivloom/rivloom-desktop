## M3.4 已确认定义

- Brain 是网络自动形成的逻辑 master 和调度域，不是 Node、用户创建的工作区或单个 AI Agent。
- 网络中没有 Brain 时自动形成一个；空白新 Node 发现已有 Brain 时不永久创建自己的 Brain。两个已经形成的 Brain 相遇后保持独立，不自动拆分、合并或迁移任务。
- 一个 Brain 当前只有一个固定活动 Master Host；一个 Node 可以承载零个、一个或多个 Brain，也可以同时服务所有受信可达 Brain。
- 开启执行能力的 Node 自动成为所有受信可达 Brain 的共享 Worker，不需要逐 Brain 加入。Brain 选择候选 Node，Node 按本机全局并发、项目、模型和额度做最终准入。
- Project 是 Node 本地普通文件夹资源。同名目录不自动等价，不要求 Git，不扫描、快照或哈希。
- 模型、凭据、额度和模型选择完全由 Node 本地管理，Brain 不维护模型池。
- Worker 向 Brain 注册静态硬件档案和动态负载；Task 可携带可选硬件硬要求。
- Task 是稳定工作记录，Execution 是 Node 上的一次执行。Project Task 固定到 Project 的 Node；Portable Task 可在合格 Worker 间重新调度。
- 新 Task 由提交 Node 自动选择一个在线且拥有匹配 Worker 的 Brain；首次发送前固定归属，此后不跨 Brain 自动迁移。
- 个人与企业复用同一最小拓扑：Brain 持有 Task，Node 承载 Master/Worker，本地 Project、模型和算力由 Node 自治；企业角色、策略、审计和计费以后作为治理层叠加，不另造一套核心模型。

## M3.4 最小闭环与验收

1. 两个独立 Brain/master 与一个共享 Worker 同时在线；不出现创建或加入 Brain 的手工操作。
2. Worker 自动出现在两个 Brain 的目录中，并通过认证加密通道向两者报告静态硬件和更新中的动态负载。
3. 两个 Brain 各自创建并持有自己的 Task，按 Project、硬件要求、执行槽和负载自动选择 Worker。
4. 同一 Worker 对两个 Brain 的并发分配执行本机最终准入，同一槽位不会产生两个活动 Execution。
5. Project Task 不离开提供其 Project 的 Node；Portable Task 可以在其他满足条件的 Worker 上重试。
6. 一个 Master Host 离线时，其 Brain 暂停新调度；另一个 Brain 继续工作，不接管离线 Brain 的 Task。
7. Brain、Task 和 Execution 路由不串线，重复消息不重复执行；硬件报告不含路径、模型凭据、硬件序列号或 MAC。
8. Release WebView2 展示 Brain/master、共享 Worker、硬件/负载、调度选择与 Task 归属；真实执行仍使用官方未修改的 OpenCode。
9. 接受及状态回传容忍协议已有的有界机器时差；取消/过期和旧 Execution 隔离仍有效，不以两机毫秒级时钟同步作为运行前提。

只有上述自动化/独立实例验证和至少两台真实 Windows 设备的核心拓扑回归通过后，才能把 M3.4 标记为 MVP 完成。同一 Brain 的自动选主与脑裂、人员身份以及跨 Brain 共同任务不属于本次验收。

### 2026-09-02 初始实现状态（历史）

已实现并自动验证：

- `brain-topology.json` 将 Brain/master 从设备密钥身份中分离；旧安装迁移为正式 Brain，新安装先形成 provisional Brain；遇到正式 Brain 会放弃空白 provisional，两个正式 Brain 不自动合并。
- 受信加密 Brain 目录周期性交换 hosted/registered Brain、队列深度和 Worker 报告。Worker 报告只含 Project ID/名称、硬件、负载和槽位；不含路径、AI 模型、Key、账号、MAC 或序列号。
- 提交 Node 先按正式/在线 Brain、队列和匹配 Worker 自动固定 Brain；远端或本机 Master 保存权威 Task，再按最新 Project、硬件、报告新鲜度、槽位和负载选择 Worker 并创建独立 Execution。Project/硬件约束随两跳幂等消息持久化。
- Worker 在节点级串行区内复核本机 Project、模型可用性、硬件报告和全局占用；Portable Task 使用本机隔离临时普通文件夹，不引入 Git、快照或哈希。
- 桌面已显示 Brain、Master Host、队列、共享 Worker、静态硬件、动态负载、项目资源、槽位和任务归属；不再让用户手选 Node/Brain。
- 普通 Worker 可以先自动固定一个 Brain，把稳定 Task 交给该 Brain 的远端 Master；Master 保存权威 Task、生成不同的 Execution ID、重新选择 Worker，并把分配/执行摘要回传提交节点。
- Worker 在全局原子准入区内完成最后一次策略、Project、模型、硬件和槽位复核后才回复接受；竞争失败会明确拒绝，不留下“已接受但未占槽”的悬空记录。

## M1 真实验证结果

1. 用户在本机“模型与额度”页面保存 DeepSeek Key，界面不回显完整 Key；真实连接测试通过且没有自动重试。
2. `deepseek/deepseek-v4-flash` 在没有 `.git` 的专用普通文件夹执行固定 slugify 编程任务。
3. 操作者拒绝一次计划外目录列举，补充约束后继续；随后分别批准预期文件编辑和 `node --test slugify.test.mjs`。
4. 独立核对确认只存在两个预期文件、测试文件未改、1 项测试通过且 0 项失败，任务最终完成验收。
5. OpenCode 官方 `session.diff` 返回空数组；界面如实显示无会话差异，没有使用 Rivloom 文件快照或内容哈希兜底。
6. 报告只记录模型标识、会话 ID、操作分类与结果，不记录 Key、完整回复或用户项目内容。

项目文件夹不要求 Git。Rivloom 不为任务建立文件快照或内容哈希；若 OpenCode 官方会话接口返回差异则展示，否则由验收人直接检查本地文件和测试记录。

## M3.3 当前已知事实

- 可信节点之间已经可以发送加密协作任务。
- 受信节点发来的任务会自动接收；本机可关闭执行能力或预设项目和模型。
- AI 操作审批已支持“请求批准 / 帮我批准 / 允许任何操作”，并通过官方 OpenCode 会话权限接口传入。
- 发起端已经能收到有序执行状态和最终摘要。
- 发起端已经能在加密任务通道上批准/拒绝具体操作、回答 AI 提问、停止远端任务、补充要求并继续同一 OpenCode 会话，以及提交最终验收；控制会校验设备信任、任务路由、唯一控制 ID 和执行序号。
- 审批和提问快照不含本机项目 ID、模型、凭据或 metadata，项目根目录若出现则显示为 `<project>`。
- 发起端可查看限长、脱敏的 OpenCode 官方会话差异；官方接口无差异时明确提示由执行机参与者本地核对，不扫描或哈希文件夹。
- 安全通道已覆盖单边会话丢失：较大 Node ID 发送签名恢复请求，由确定的较小 Node ID 重建通道，避免双方并发握手。
- 2026-09-02，Win11 `192.168.5.20` 与当前开发机 `192.168.5.33` 已用真实 DeepSeek 和普通文件夹完成单人双机闭环：可信任务自动接收、远程一次性批准文件写入、生成文件、补充要求后续跑同一 OpenCode 会话、本地核对结果和归属端最终验收均通过。
- 本次发现 `5.33` 上随包 `node.exe` 的 TCP/UDP 入站规则虽已启用但 `Action=Block`；改为 Private Profile 的 Allow 后，`5.20 → 5.33` TCP 探测和自动发现恢复。安装器尚未可靠创建、检测或修复规则；该项已延后优化，不阻塞 M3.4。
- 产品功能已形成“发送 → 自动执行 → 人工介入 → 补充 → 查看结果 → 验收”闭环；单人双机核心体验已验收，M3.3 的 MVP 范围完成。
- 远程停止、另外两种审批、撤销信任、异常断网恢复、两真人角色回归及防火墙安装体验保留为明确的后续优化，不作为当前推进阻塞项。
- 当前“单个可复用项目和模型”的实现是 M3.3 已验收切片；它不预先决定 M3.4 的 Brain 与资源模型。

## 暂停与延后项

- 同一 Brain 的状态复制、自动选主、Master 迁移、任期 fencing 和脑裂处理；不影响当前已实现的 Worker Execution ID fencing。
- 人员身份、一人多节点、一节点多人、企业角色与跨 Brain 共同任务。
- Brain 按规模或负载自动拆分、创建或合并。
- 不用旧的 30 分钟准备租约流程。
- 不优先开发 ChatGPT 登录、更多模型供应商、自动更新或正式发行签名。
- 不把尚未完成的两真人、停止/自动审批/撤销及防火墙回归描述成已验证；它们已记录为后续优化。
